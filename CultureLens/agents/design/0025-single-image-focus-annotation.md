# Design 0025：单图显眼框目标标注

- 状态：已实施
- 日期：2026-08-01
- 影响范围：框选交互、图片预处理、iOS 识别请求、扫描结果与历史图片
- 前置设计：
  - `0006-focused-recognition-and-evaluation.md`
  - `0021-owned-image-data-across-concurrency.md`

## 1. 问题

现有框选页的角点手势应用在定位布局之后，多个角点的命中区域会在父容器中重叠，真机表现为只有一个
角点能够稳定拖动。

现有识别流程还会把方向归一后的图片裁成第二张特写，并发送“整图 + 特写”两张图片。双图保留了上下文
和局部分辨率，但增加了图片处理、请求体和模型跨图对应复杂度；结果页与历史只保存裁剪特写，也会丢失
用户拍摄时的完整现场。

## 2. 决策

改为“完整原图 + 像素级显眼框”的单图输入：

1. 框选页继续允许移动矩形和拖动四角调整大小。
2. 确认后不再裁剪图片，而是在方向归一后的完整 JPEG 上绘制目标框。
3. 标注框使用白色外描边和朱红色内描边，兼顾深色、浅色和复杂背景；不添加文字，避免遮挡对象或引入
   OCR 噪声。
4. 识别请求只发送这张带框完整图，不再由 iOS 填充 `focus_image_base64` / `focus_mime_type`。
5. 请求的 `context_note` 明确说明矩形框由 App 添加、框内是用户目标、框外只用于场景和尺度上下文。
6. 结果页和扫描历史保存带框完整图，使用户可回看当时询问的目标及其现场位置。
7. “识别整张图片”继续发送无标注的完整图，不附加框选说明。

后端现有双图字段继续保留，以兼容旧客户端、评测工具和其他调用方；本次不修改公开 API。

## 3. iOS 数据流

```text
Camera / PhotosPicker
  -> ImagePreprocessor.normalizedJPEG
  -> FocusSelectionView
       -> 识别整张：NormalizedImageRegion = nil
       -> 框选识别：NormalizedImageRegion
  -> ImagePreprocessor.annotatedJPEG（仅框选识别）
  -> RecognitionInput.imageData：无框整图或带框整图
  -> context_note：仅框选时增加固定目标框说明
  -> RemoteRecognitionService（单图请求）
  -> ScanResultView / ScanHistory：保存本次实际发送的完整图
```

`NormalizedImageRegion` 仍使用左上角归一化坐标，且只属于本次短期编辑状态，不写入 SwiftData。

## 4. 框选手势

- 每个角点先建立独立 44 × 44 pt 命中区域并绑定手势，再使用 `.position` 放到对应角点。
- 可见圆点维持 26 pt，命中区域满足触控目标尺寸且不改变视觉比例。
- 四角使用各自的枚举值计算边界；拖动开始时固定起始 region，结束时清空手势状态。
- 框内部仍可整体移动，框和四角始终限制在图片可见范围内。

## 5. 图片标注

- 输出像素尺寸与归一化原图一致，继续编码为无 EXIF/GPS 的 JPEG。
- 描边宽度按图片短边比例计算并设置最小值，避免在不同分辨率下过细。
- 描边完全收进图片边界，框贴近边缘时不被裁掉。
- 不降低框外亮度，不填充框内，不改变框内图像内容。

## 6. LLM 影响与边界

单图显眼框让目标和现场上下文处在同一坐标系，避免模型在两张图之间建立对应关系，对中等及以上尺寸的
目标通常更直接。固定提示文字用于消除“矩形是现场物体还是 App 标记”的歧义。

它不保证对所有图片都优于裁剪特写：当目标在 1600 px 整图中仍非常小时，裁剪图可能提供更多有效像素。
因此离线评测继续保留 `whole`、`crop` 和 `context-focus` 作为对照，并新增带框单图策略后再下最终结论。

## 7. 验证

- 单元测试：带框输出尺寸不变、JPEG 可解码、无 GPS/EXIF、与无框原图字节不同。
- 单元测试：`RecognitionInput` 只预编码本次实际发送的一张图片。
- 编译：iOS Simulator Debug 与 iPhoneOS arm64 `build-for-testing`。
- 真机：分别拖动四个角点与框内部，确认每个方向都能调整且边界限制正确。
- 端到端：确认请求只含一张带框图，结果页和历史显示同一张完整图。
