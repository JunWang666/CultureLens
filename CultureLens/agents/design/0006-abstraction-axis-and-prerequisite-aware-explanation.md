# 0006 关系抽象轴、抽象阶梯与前置知识感知讲解

- 状态：已设计（待实现，2026-08-04）

## 背景

立项书的核心体验是「从看见走向看懂」：用户拍到三潭印月，应该能顺着
`三潭印月 → 西湖 → 苏堤 → 苏轼 → 宋代 → 中国朝代` 一路把眼前对象放回更大的文化脉络；
图谱上应该标出前置知识，讲解时自动补上用户尚未掌握的前置，并据关联知识与用户倾向给出补充与下一步建议。

产品里看不出这条链路。核查后结论是：**这条链路已经存在于知识包数据中，且关系类型正好编码了抽象方向，但被代码在三处丢掉了。**

用真实西湖包跑最短路，带类型输出：

```
三潭印月 --[位于]--> 西湖文化景观
三潭印月 --[位于]--> 南宋西湖十景体系 --[组成]--> 苏堤春晓
苏堤春晓 --[产生于]--> 苏轼与西湖治理
三潭印月 --[产生于]--> 北宋疏浚与三潭石塔 --[体现]--> 宋代山水审美
```

### 三处丢弃点

1. `KnowledgeStore` 把有向带类型关系压成无向无标签邻接表。`relations` 保留了端点顺序与
   `kind` / `explanation`（源码注释已说明），但 `adjacency: [String: [String]]` 双向插入且不带类型。
   全 App 只有这一个遍历原语，因此图谱 BFS、`relatedElements`、讲解取邻居看到的都是无向无标签的球。
   同心环按 hop 分环，只能画出「球」，画不出「梯子」。

2. 讲解只能看到 1 跳、8 个、按名称字母序截断的邻居。`CultureExplanationService.neighborContexts`
   只调 `store.relatedElements(forKey: rootKey, limit: 8)`，而该方法排序为 `($0.name, $0.key)`。
   模型物理上看不到 hop 1 以外的节点，5 跳的阶梯无从知晓；哪 8 个邻居进 prompt 由中文排序决定，
   而不是「对理解最关键」或「用户还不知道」。

3. 没有任何前置知识计算。`explainUserText` 传的 `user_knowledge_states` 是全部已加入节点的平铺列表，
   既未标出与当前对象的相关性，也未计算「该对象的前置里用户还差哪些」。`explain.txt` 只有软规则
   （掌握 / 理解 / 接触各自怎么讲），落在那个字母序 8 邻居列表上。

### 数据侧现状

| 项目 | 实测 |
| --- | --- |
| `理解前先懂` 边 | 全包 **3 条**（182 条关系中），且全是对象内部微观细节，无一在抽象阶梯上 |
| `kind` 覆盖 | 西湖包 94/182（51.6%）；浙博 / 良渚 / 中国历史三包 0/310 |
| `conceptKind` 覆盖 | 西湖包 70/70；其余三包 0/106 |
| 跨包关系 | 0 条，四包完全不连通 |
| 阶梯顶端 | `宋朝` / `中国历代王朝脉络` / `中华文明五千年` 在 `KnowledgePackChineseHistory` 内，该包被排除出 build 且无法被加载 |

阶梯正好断在离开西湖包的地方：西湖包内能走到 `宋代山水审美`，再往上就出包了。

## 目标

- 让 `三潭印月 → … → 中国历代王朝脉络` 这条链路在产品中可见、可点、可继续探索。
- 图谱显式表达前置知识，并区分用户已掌握与未掌握。
- 讲解自动补齐未掌握前置，并基于关联知识与用户倾向给出补充与下一步建议。

## 非目标

- 不引入力导向布局（0002 已论证并否决，保持确定性纯函数布局）。
- 不做知识包热更新（ODR 仍随版本发布）。
- 不改动识别管线的候选挑选与 `v5` 契约。

## 设计一：关系抽象方向表

给 `RelationKind` 增加静态方向分类，**不改知识包 schema**：

| 方向 | RelationKind | 语义 | 实测条数（西湖包） |
| --- | --- | --- | --- |
| 上行（source 更具体 → target 更抽象） | `位于` `体现` `受到影响` `受规制于` `解释` | 指向更大的语境、原则或影响源 | 21 / 22 / 7 / 1 / 5 |
| 下行（source 更抽象 → target 更具体） | `组成` | 整体指向部分 | 10 |
| 横向 | `相似于` | 同级类比 | 6 |
| 上行，但须先审计取向 | `产生于` | 指向来源与成因 | 4 |
| 待定（先按横向处理） | `用于` `象征` `制作采用` | 数据中取向不一致 | 8 / 5 / 2 |
| 前置轴（独立于抽象轴） | `理解前先懂` | source 为前置，target 为依赖 | 3 |

方向依据来自实测样本，例如 `三潭印月 --位于--> 西湖文化景观`（narrower → broader）、
`三潭印月 --组成--> 三座水中石塔 --组成--> 石塔圆孔`（broader → narrower）。
`理解前先懂` 的方向与 `CultureRelationGraphView.prerequisiteCount` 现有判断
（`kind == .prerequisiteFor && targetID == object.id`）一致，无需改动。

### 已确认的数据缺陷（必须先修，否则阶梯会算错）

**`产生于` 存在反向边。** 全部 4 条中有 2 条取向与类型名相反：

| 边 | 判定 |
| --- | --- |
| `三潭印月 => 北宋疏浚与三潭石塔` | 正确 |
| `湖滨城墙与城门记忆 => 西湖文化景观` | 正确 |
| `南宋临安与西湖十景 => 西湖十景的观看方式` | **反向**，其 explanation 写的是「十景观看方式由此成型」 |
| `苏轼与西湖治理 => 苏堤春晓` | **反向**，应为 `苏堤春晓 产生于 苏轼与西湖治理` |

后果已实测：把 `产生于` 计入上行后，`苏堤春晓` 会被算成 `三潭印月` 的 L3 祖先，
而它实际是同级景目。**错误的阶梯比没有阶梯更糟**，因此 `产生于` 必须先做取向审计再纳入上行集合。

**上行图存在 1 个环，且由同一批反向边造成：**

```
西湖文化景观      --[受到影响]--> 南宋临安与西湖十景
南宋临安与西湖十景 --[产生于]-->  西湖十景的观看方式     ← 反向边，闭合了这个环
西湖十景的观看方式 --[受到影响]--> 1985 西湖新十景
1985 西湖新十景   --[位于]-->    西湖文化景观
```

实测：把 `产生于` 计入上行时上行边 70 条、环 1 个；移出后上行边 66 条、环 0 个。
即**这个环完全由 `产生于` 的反向边造成**，修数据即可消除，不需要为环设计特殊规则。

顺带应一并审计 `西湖十景的观看方式 --受到影响--> 1985 西湖新十景`：按 `受到影响` 的既有用法
（target 为影响源），它表示历史观看传统受 1985 年题名影响，时间上讲不通，取向应相反。

层级推导仍需保留环检测作为兜底，且导出工具应把环作为错误拦下。

## 设计二：有向遍历 API

`KnowledgeStore` 保留现有无向 `adjacency` 不动（避免影响识别候选与现有图谱快照），另建有向索引与查询：

- `upward(key:) -> [(key, kind, explanation)]` / `downward(key:)` / `lateral(key:)`
- `ancestors(key:maxLevels:) -> [AbstractionLevel]`：沿上行边逐层展开，环上节点只取首次到达的层级
- `siblings(key:) -> [String]`：与自身共享至少一个上行父节点的节点
- `missingPrerequisites(key:known:maxCount:)`：沿 `理解前先懂` 反向求传递闭包，与已掌握集合求差集

全部为纯函数，可在无 Mac 环境下单测。

## 设计三：阶梯 = 祖先链 + 同级相关

一个必须记录的认知：**用户举的链条不是单调上行的。**

`三潭印月 --位于--> 南宋西湖十景体系 --组成--> 苏堤春晓`——`苏堤` 是先上行再下行才到达的，
它与 `三潭印月` 共享父节点 `南宋西湖十景体系`，是**同级景目**而非祖先。

因此阶梯 UI 不能只做单调祖先链，形态定为「纵向祖先链 + 每级横向同级相关」：

- 纵向（前四级为现有数据实测可达，后两级需跨包桥接）：
  `三潭印月 › 西湖文化景观 › 南宋临安与西湖十景 › 宋代山水审美 › 宋朝 › 中国历代王朝脉络`
- 横向：在 `南宋西湖十景体系` 这一级给出 `苏堤春晓` 等同级 chips

实测 `三潭印月` 的祖先分层。取**已验证无环的保守上行集合**（不含待审计的 `产生于`）：

```
L1  湖中湖、岛中岛、园中园 / 西湖文化景观 / 西湖月景与倒影营造 / 南宋西湖十景体系 / 小瀛洲的湖中园林格局
L2  诗画化的景名 / 南宋临安与西湖十景 / 西湖十景的观看方式 / “小瀛洲”的名称来源
L3  宋代山水审美 / 1985 西湖新十景
```

**即使不动任何数据，`三潭印月` 也已经能沿上行边走到 `宋代山水审美`**（含 `产生于` 时它提前到 L2），
实际路径为：

```
三潭印月 › 西湖文化景观 › 南宋临安与西湖十景 › 宋代山水审美
```

这是阶梯可行性的关键验证点，也是阶段 1 单测应当断言的具体事实：不依赖任何内容补全即可跑通。

同一层出现多个祖先时，按上行边类型优先级排序（`位于` > `体现` > `受到影响` > `解释`）取一条作为主干，
其余降级为该级的同级相关，避免阶梯分叉成树。

## 设计四：多包合并与跨包桥接

阶梯顶端出包，所以多包必须先解决：

1. 三个包从 `project.pbxproj` 的 `membershipExceptions` 放出，按包给 ODR tag。
2. `KnowledgeStore.load` 从单包硬编码（`subdirectory: "KnowledgePack"` + 单个 `knowledge-pack.json`）
   改为多包发现与合并。
3. **键冲突必须处理**：良渚包与浙博包都定义了 `shi-xingeng-discovery`，而
   `DeterministicID.culturalElement(key)` 对相同 key 产出相同 UUID，朴素合并会把两个不同元素静默塌成一个节点。
   方案（待定）：给 key 加包命名空间前缀，或在 `DeterministicID` 中掺入 packVersion。
   任一方案都会改变既有 UUID，需要同步迁移 `KnowledgeProgressRecord.nodeID`，否则用户已加入的节点会全部失联。
4. 跨包关系需要显式机制：允许 `relations` 引用其他包的 key，或单独维护 `bridges.json`。
   第一批桥接边即 `宋代山水审美 → 宋朝 → 中国历代王朝脉络 → 中华文明五千年`。

## 设计五：prompt 契约变更

`explainUserText` 的 payload 增加两个字段：

- `abstraction_path`：祖先链，每级带 `key` / `name` / 一句摘录，**上限 5 级**
- `missing_prerequisites`：未掌握前置闭包，带原文 fragment，**上限 3 条**

邻居选择从「字母序前 8」改为按轴分配名额：上行 2–3、未掌握前置全取、横向 2、其余补位。
同时 `user_knowledge_states` 从全量平铺改为「与当前对象相关的子集 + 总数计数」，
避免 payload 随使用无限增长且模型抓不到重点。

`explain.txt` 输出结构从两节扩为三节：

```
## 先理解          （仅当 missing_prerequisites 非空时出现）
## 文化背景
## 下一步建议
## 引用来源
```

新增硬规则：`先理解` 的内容只能来自 `missing_prerequisites` 的 fragment；
`abstraction_path` 用于在 `文化背景` 结尾把对象放回大脉络；
`下一步建议` 优先指向祖先链的下一级或某条未掌握前置。
现有「实质内容必须严格来自 knowledge_fragments」的约束继续覆盖新字段，因此不引入编造风险。

`ScanResultView` 的分节解析与引用抽取需同步改；历史中已存的两节格式旧讲解要能共存。

## 设计六：用户倾向

立项书要求「根据用户偏向」给出补充，但 App 当前**没有任何偏好数据源**。
最省的做法是从已加入节点的 `ConceptKind` 分布推导倾向（偏审美 / 偏历史 / 偏技法），
作为 prompt 的 `preference_profile` 字段。不引入显式偏好设置页。

## 内容工作量与校验门槛

代码改动是增量的，真正的瓶颈在内容：

- 补 `理解前先懂` 边：现有 3 条远不够支撑「自动附加未掌握前置」。目标是核心对象（十景、主要景点、
  主要器物）各 2–3 条。可半自动：上行的 `位于` / `体现` 边天然是前置候选，人工确认取向即可。
- 补 `kind`：西湖包缺 88 条，三包缺全部 310 条。**没有 kind 就没有方向，没有方向的边进不了阶梯。**
- 补 `conceptKind`：三包缺全部 106 个，否则新内容全部回落 `.foundation`，节点同色同图标。
- 审计 `产生于` 等取向不一致的边，修掉那 1 个环。

导出工具需新增校验并作为 CI 门槛：`kind` 覆盖率 100%、上行图无环、
每条 `理解前先懂` 边的两端都存在、跨包桥接引用的 key 可解析。

## 分阶段任务

**阶段 1（遍历层，不依赖内容补全即可验证）**

1. `RelationKind` 方向表 + `AbstractionDirection` 枚举。
2. `KnowledgeStore` 有向索引与 `upward` / `downward` / `lateral` / `ancestors` / `siblings` /
   `missingPrerequisites`，含环检测。
3. 单测：以真实西湖包为输入，断言 `三潭印月` 的祖先链能走到 `宋代山水审美`；
   前置闭包对现有 3 条边结果正确；环上节点层级唯一且确定。

**阶段 2（内容与多包）**

4. `产生于` 取向审计 + 修掉 1 个环。
5. 导出工具校验 + CI 门槛。
6. 多包合并加载、key 命名空间、`DeterministicID` 迁移、跨包桥接。
7. 补 `kind` / `conceptKind` / `理解前先懂` 覆盖。

**阶段 3（讲解层）**

8. `explainUserText` 新字段 + 邻居名额分配 + `user_knowledge_states` 收窄。
9. `explain.txt` 三节输出与硬规则。
10. `ScanResultView` 分节解析改造与旧格式兼容。

**阶段 4（UI 层）**

11. 抽象阶梯条（扫描结果 / 对象详情顶部，可点、可换起点、带同级 chips）。
12. 图谱按方向分层 + 前置节点显式标记（与 `0007` 的布局改造合并实施，避免做两遍）。

## 验证

- 阶段 1 全部为纯函数，可在无 Mac 的 Cloud 环境用真实知识包跑单测，断言具体事实
  （如「三潭印月的上行链能走到宋代山水审美」），不依赖 UI。
- 阶段 2 的校验以导出工具退出码为准。
- 阶段 3 需实测首 token 延迟：payload 变长后确认 `reasoning_effort: low` 下无明显退化。
- 阶段 4 需 Mac + Xcode 模拟器与真机验证。

## 风险

- **prompt 体积**：祖先链 + 前置闭包会显著变长，必须按上限截断。
- **UUID 迁移**：多包 key 命名空间会改变 `DeterministicID`，处理不当会让用户已加入节点全部失联。
- **讲解契约变更**：两节改三节属于破坏性变更，需兼容历史中已存的旧格式讲解。
- **错误的阶梯**：取向缺陷不先修，阶梯会给出语义错误的层级（已实测 `苏堤春晓` 被误判为祖先）。

## 被否决的替代方案

- **在知识包新增显式 `level` 字段**：需要人工为 176 个元素标层级，且层级本身随包合并而变动；
  由上行边推导更稳，且能复用已有的 94 条类型化边。
- **让 LLM 自己推断抽象层级**：与「实质内容必须来自 knowledge_fragments」冲突，且不可复现、不可测。
- **把祖先链做成单调树**：与实测数据不符——用户举的链条包含同级横向跳（`苏堤`），
  强行单调会把同级景目误标为祖先。
