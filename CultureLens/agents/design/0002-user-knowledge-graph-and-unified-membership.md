# 0002 用户文化图谱与统一加入状态

- 状态：已实现（2026-08-03）

## 背景

当前“图谱”Tab 只按类别列出被标记为“已了解”的历史概念，没有使用知识包关系画图；对象详情又同时出现不持久化的“收藏”和持久化的“我已经了解”，三个入口表达的是同一件事却读写不同状态。对象详情内的关系图虽然能展示识别结果随附的关系，但不能从全局图谱选择中心继续探索。

## 产品语义

- 用户状态命名为「加入文化图谱」/「已加入图谱」，并细分为接触 / 理解 / 掌握三级（任一非空级别均算已加入）。
- 原「我已经了解」「已了解」「收藏」入口统一读写 `KnowledgeProgressStore`；不再保留详情页临时收藏状态。
- 已有 `culturelens.understood-node-ids.v1` 数据在 `KnowledgeProgressStore` 绑定 model context 时迁移到 SwiftData `KnowledgeProgressRecord`（含 `updatedAt` 与 `source`），旧「已了解」节点保留为 `.understand`。UI 可直接选择三级，也可移出图谱。
- 识别 summary、现场讲解与追问 prompt 携带用户知识状态，并遵循「跳过已知、锚定已知、补缺」。
- 图谱 Tab 的可见节点 = 所有已加入且能在知识包解析的节点 + 从当前中心按无向关系 BFS 向外最多 3 跳的节点。已加入但超出当前中心 3 跳的节点仍显示在外层，避免用户资产因换中心而消失。
- 用户可从当前可见节点中选择新中心；换中心只重算局部快照与布局，不修改加入状态。

## 数据与算法

`KnowledgeStore` 在加载知识包时建立以下只读索引：

- element key → element
- deterministic UUID → element key
- element key → 已排序邻接节点

新增图谱快照查询，输入为 `centerID`、已加入 ID 集合、`maxDepth = 3`、扩展节点上限（当前为 48）。查询步骤：

1. 将已加入 ID 映射为知识包 element key；首个已加入节点作为默认中心。
2. 从中心做队列式 BFS，记录最短跳数，深度到 3 即停止。
3. BFS 扩展节点达到上限后停止继续入队；所有已加入节点不受扩展上限影响。
4. 对最终可见节点集合筛选诱导子图关系边；边按 key 排序，保证布局和测试确定。

当前知识包只有 34 节点 / 44 边。扩展默认仍设显式节点上限，以便未来知识包增长后控制 SwiftUI 节点数、内存和布局开销。

## 布局与渲染

采用确定性同心最短路布局，而不是持续迭代的力导向布局：

- 中心在画布中央；1、2、3 跳分别进入同心环。
- 超出当前中心 3 跳但已加入的节点进入最外“其他已加入”环。
- 每环半径同时满足最小层间距和按节点数估算的圆周间距，节点按名称/key 排序后均匀排布。
- 关系边用单个 SwiftUI `Canvas` 批量绘制，节点保留为可访问的 SwiftUI 控件。
- 布局是纯函数，只在知识包、中心或加入集合变化时重建；不启动定时器、物理模拟或逐帧动画。

该方案复杂度为 O(V + E)，视觉上明确表达“离中心几跳”，也与“向外 3 层”的产品含义一致。力导向布局在小图上更有机，但会带来迭代成本、位置抖动与不可复现结果，因此不采用。

## 导航与兼容

- `AppRoute` 增加按知识包 element key 打开概念详情的路由；详情通过 `KnowledgePackLoader` 读取当前 ODR/fallback 知识包，使尚未出现在扫描历史中的外扩节点也可查看。
- 无法映射到当前知识包的旧节点 ID 不参与关系扩展；界面会统计提示，但保留其持久化状态，避免静默删除用户数据。
- `ScanHistoryRecord.isBookmarked` 暂保留以避免 SwiftData schema 破坏；当前 UI 不再读写它，后续做显式模型迁移时再移除。
