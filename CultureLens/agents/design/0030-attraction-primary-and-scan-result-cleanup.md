# 0030 景点主结果识别与扫描结果页收敛

## 背景

当前识别协议只能返回文化元素作为主对象，附近景点只能作为 alternatives，因此画面明确是“三潭映月”时，标题仍可能显示其关联文化元素“北宋疏浚与三潭石塔”。结果页还把位置排序解释和通用说明混在判断卡片/对象详情中，干扰用户确认景点。

## 目标

- 让模型可以明确声明主结果是附近景点，并返回服务端提供的原始 `attraction_key`。
- 只有模型确认画面目标就是景点时才提升景点为主结果；不能仅凭距离自动提升。
- 景点主结果仍可挂载其对应文化元素的图谱和介绍，保留文化知识上下文。
- 从扫描结果判断卡片删除“位置调整了候选顺序”及位置影响说明。
- 将判断卡片移动到景点候选区域之后，作为候选确认辅助信息。
- 删除对象详情中的“先看结构，再看装饰”说明卡片。

## 协议与数据流

Provider 主结果新增可选 `attraction_key`：

```text
attraction_key = 附近介绍中的 attraction_key，确认目标是该景点时填写；否则为空
```

服务端验证 key 必须来自当前位置返回的景点集合。命中后使用景点名称作为主标题，并使用其关联文化元素生成图谱；未命中或为空时保持原文化元素/LLM 主结果逻辑。`alternatives` 仍只输出景点候选。

## UI

- 扫描结果顺序调整为：识别对象 → 文化知识图谱 → 附近景点候选 → 判断依据 → 保存。
- 判断依据保留视觉 rationale 和必要的不确定性，但不再显示位置影响段落。
- 删除对象详情的通用“先看结构，再看装饰”卡片。

## 验证

- Go pipeline/provider/API 测试覆盖合法、非法和空 `attraction_key`。
- 运行 `go test ./...`、`go vet ./...`。
- iOS 执行 `git diff --check` 和可用的 Xcode 编译检查。
