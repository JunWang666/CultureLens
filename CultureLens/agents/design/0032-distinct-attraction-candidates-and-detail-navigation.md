# 0032 景点候选去重、真实介绍与独立详情导航

- 日期：2026-08-02
- 状态：已确认，已本地实施，待部署
- 影响范围：Go 识别响应、景点候选数据、Swift 扫描结果导航、概念详情展示
- 前置设计：`0028-separate-attraction-candidates-from-cultural-knowledge.md`、`0029-persist-candidates-and-history-graph-ui.md`、`0030-attraction-primary-and-scan-result-cleanup.md`

## 问题

1. 模型已经把某个景点确认成主结果后，后端仍把同一个景点加入 `alternatives`，结果页因此出现两个同名选项。
2. 景点候选只携带固定文案“来自当前位置附近的景点现场介绍”，没有返回数据库中已经审核的现场介绍。
3. 候选卡片只切换当前页状态，用户还要再次点击保存或阅读按钮，交互上没有进入候选自己的内容页。
4. 图谱概念的 `summary` 与 `detail` 被后端赋成同一文本，客户端又无条件渲染两段，造成基础知识重复。

## 决策

### 候选响应

- `AttractionCandidate` 增加 `Summary`，取该景点按距离排序后的第一条审核现场介绍纯文本。
- Provider 明确返回 `attraction_key` 并提升为主景点时，响应 `alternatives` 排除同 key 景点；其余候选保持按 Repository 顺序，最多 3 条。
- 景点候选的 `summary` 返回审核现场介绍；`rationale` 只说明它为何出现在候选集合中，不再承担景点介绍。
- App 额外按主结果名称做兼容去重，避免尚未升级的服务响应继续显示重复主景点。

### 导航

- `AppRoute` 增加由扫描会话 ID 与候选 ID 组成的候选详情路由。
- 扫描结果页的候选卡片改为 `NavigationLink`，点击后直接进入独立“候选详情”页面。
- 候选详情展示候选名称、数据库现场介绍和候选依据，并在该页完成确认保存；保存快照继续记录原始识别结果、最终对象和候选 ID。
- 主扫描结果页只保存主结果，不再通过候选卡片原地替换标题和摘要。

### 旧服务响应的候选详情补全

- 已部署旧服务只返回景点 key、名称和固定位置说明时，App 不把固定说明冒充为候选正文。
- 候选详情使用本次扫描位置调用现有附近介绍 API，再按 `attraction.key` 过滤，读取该景点的审核现场介绍。
- 第一条非重复现场介绍作为候选摘要，其余不同介绍作为现场知识条目展示；正文按去空白文本去重。
- 固定的“位置候选、仍需画面确认”语义只显示一次，不再同时出现在标题正文与依据卡片。
- 无位置、无匹配内容或请求失败时明确显示内容不可用状态，不重复兜底文案，也不伪造景点介绍。

### 概念正文

- 后端不再用摘要复制填充 `detail`；没有独立长文时返回空字符串。
- App 对旧快照和旧服务响应做兼容：只有 `detail` 非空且与 `summary` 去空白后不同，才显示第二段正文和分隔线。

## 兼容与验证

- JSON 只新增已有候选 `summary` 的赋值，不新增公开字段；旧 App 可忽略，旧服务仍可被新 App 客户端去重。
- 历史快照结构不变，不升级 SwiftData 容器。
- Go 测试覆盖主景点排除和真实候选介绍；Swift 测试覆盖旧重复候选过滤及重复概念正文隐藏。
- 执行 `go test ./...`、`go vet ./...`、Swift 单元测试或可用的 iOS 编译检查及 `git diff --check`。
